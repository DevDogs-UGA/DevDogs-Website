# @devdogsuga/sdk

The DevDogs SDK for TypeScript: one package with a subpath for each thing the
club's apps share. Import from a subpath (`@devdogsuga/sdk/brand`), not the root.
The Dart half is [`devdogsuga_sdk`](../sdk_dart/README.md).

| Subpath                                                                                        | What it is                                                                                                                         |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `brand` (and `brand/event`, `/marks`, `/qr`, `/render`, `/next`, `/palette.css`, `/artwork/*`) | The palette, fonts, artwork, the DogDays and DogPack marks, the image templates. See [BRAND.md](./BRAND.md).                       |
| `env` (and `env/derivation`, `env/targets`)                                                    | The env registry machinery: `declare`, `define`, `createEnv`, the deploy targets. See [ENV.md](./ENV.md).                          |
| `db/client`, `db/server`, `db/typegen`                                                         | Supabase and Drizzle client factories. See [DB.md](./DB.md).                                                                       |
| `headers`                                                                                      | Security headers, the CSP builder and nonces. See [HEADERS.md](./HEADERS.md).                                                      |
| `telemetry`                                                                                    | Sentry options, the scrubbers and `alert`. See [TELEMETRY.md](./TELEMETRY.md).                                                     |
| `moderation`                                                                                   | The moderation protocol: message schemas, Standard Webhooks signing, the report client, signed samples and the reference receiver. |
| `catalog`                                                                                      | The generated client for the public UGA course catalog API (`/catalog/v1`).                                                        |
| `platform`                                                                                     | The generated client and types for the platform's public API (`/moderation/v1`).                                                   |
| `client`                                                                                       | The fetch runtime under the two generated clients, and `ApiError`.                                                                 |
| `constants`                                                                                    | Hosts, paths, the OAuth provider and its tiers, header names: the values both SDKs share.                                          |

## Generated code

`catalog`, `platform` and `constants` are generated by `@devdogsuga/sdk-spec` from its OpenAPI files
and `constants.json`; do not edit `src/*/generated.ts`. Run `pnpm -F @devdogsuga/sdk-spec codegen`
after changing a spec, a zod schema in `moderation`, the palette or the telemetry scrub rules: CI
regenerates in memory and fails on any difference.

## The catalog client

```ts
import { createCatalogClient } from "@devdogsuga/sdk/catalog";

const catalog = createCatalogClient({
  baseUrl: process.env.CATALOG_URL!, // https://api.devdogsuga.org/catalog/v1 (staging: api-staging)
  client: "dogdays/1.0", // sent as X-Client, for usage numbers only
});
const { terms } = await catalog.listTerms();
const found = await catalog.searchCourses({
  term: 202702,
  q: "intro to programming",
});
```

`baseUrl` is required so staging and production are the same code. A refused request throws
`ApiError` (`status`, `code`, `retryAfterSeconds`).

## Prereleases

Every green push to `main` publishes changed packages to the `next` dist-tag, as
`<next patch>-next.<run number>`. Products pin `next` until the stable bump lands.

```sh
pnpm add @devdogsuga/sdk@next
```

How that is wired, and what a maintainer must set up once:

- npm prereleases go out on **every green push to `main`** (Q88: publishing happens from `main` only), not on a
  tag push, through the reviewer-less `publishing-next` environment (`ci.yaml` job `publish-next`, which calls
  `publish.yaml` with `channel: next`). Only the Dart SDK publishes by **tag push**
  (`devdogsuga_sdk-vX.Y.Z-next.N`, see `.github/workflows/publish-dart.yaml`), because pub.dev authenticates a tag.
- **The two SDKs version independently.** The npm package takes one patch past the highest version on npm (the
  `0.0.0` placeholder), so its first prerelease is `0.0.1-next.N`. The Dart package takes the `0.1.0` in
  `packages/sdk_dart/pubspec.yaml`, so its first is `0.1.0-next.N`. Nothing pairs them: a product pins each from its
  own registry, and the committed `0.1.0` in `packages/sdk/package.json` is never published as such. What ties
  them is the spec: `check:drift` fails when either generated client differs from `packages/sdk-spec`.
- npm Trusted Publishing for `@devdogsuga/sdk`, `devtools`, `config` and `backstage` must name this repository and
  the workflow file `publish.yaml`, with the **environment field left blank**. An environment of `publishing`
  would refuse the `publishing-next` job, and one of `publishing-next` would refuse the stable job.
- pub.dev automated publishing for `devdogsuga_sdk` takes the tag pattern `devdogsuga_sdk-v{{version}}`.
- The five packages merged into the sdk are deprecated by `node scripts/deprecate-old-packages.mjs --apply`
  (a maintainer, signed in to npm).
